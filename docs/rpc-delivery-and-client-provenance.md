# RPC 结果交付与客户端归属修复

## 修复范围

本次修复不改变工具名称、输入参数、权限策略、鉴权规则、平台检查或执行通道。

### RPC 响应已经收到，却没有通知等待者

旧实现先从 `pending` 删除请求，再记录 `rpc_result` / `rpc_error`。记录异常会中断处理，使该请求既不在待处理集合里，也没有完成结果。其他并行请求还可能被错误标为连接丢失。

新实现保留响应处理，发送后的日志异常不影响 Future 完成。原始成功结果、官方错误码和断开连接结果均保持真实，不自动重复执行。

### 请求已发送，发送日志失败却删除待处理请求

新实现将必须成功的 `rpc_dispatch_intent` 放在实际发送前；无法记录时抛出 `audit_unavailable`，不发送该请求。实际发送后的 `rpc_send`、结果日志及清理日志属于已发生操作的观测，记录异常不能把执行结果抹去。

新增 `diagnostics.rpc_audit_error_count` 和 `diagnostics.rpc_audit_status`。审计对象中的失败计数仍保留。执行前的审计要求没有降低；本修改不允许在审计不可用时启动新请求。

不支持的官方回调仍返回 `-32601`，不会因日志故障被批准。

### 无状态请求借用别的客户端信息

旧实现通过进程全局的“最后一个 initialize”推断当前客户端，可能将客户端 A 的名称和能力展示给客户端 B。相同账号或相同访问凭据也不能证明是同一个连接。

已移除该全局推断。无状态请求在没有绑定的 initialize 参数时返回：

```json
{
  "observed": false,
  "source": "stateless_http_no_client_binding",
  "reason": "No initialize parameters are bound to this request."
}
```

有状态会话仍报告自身实际协商的客户端能力。此修改只修正归属报告，不关闭浏览器、桌面或命令执行功能。

## 验收方式

`tests/test_rpc_audit_delivery.py` 在内存协议夹具中检验发送前审计失败、发送后日志异常、成功/错误响应、并行响应、通知与回调处理。`tests/test_client_provenance.py` 通过真实 MCP SDK 的 HTTP 管理器及有状态会话检验客户端归属。

新增 11 个用例在修复前的结果为 10 失败、1 个正常有状态对照通过。修复后相关 30 个用例通过。完整测试和真实 Codex 运行环境验收的原始结果仅保存在本机 `evidence/`，不上传原始日志。

## 与平台拦截的区别

这些是已复现的本机缺陷，不构成平台拦截的根因证据，也不意味着平台拦截已解除。无平台请求编号时，不能仅凭共享服务日志中缺少记录就断言请求绝对没有送达。

源码提交、测试通过、正式服务加载、GitHub 同步必须分别取得实际回执，不得互相替代。
