# 原生维护入口与 HTTP 到达证据

## 原生维护

项目维护优先使用 `scripts\Maintain-Core.cmd`，不再依赖先调整 PowerShell 脚本执行策略。

```bat
scripts\Maintain-Core.cmd --check
scripts\Maintain-Core.cmd --restart
```

无参数时与 `--check` 相同，只检查既有维护控制器；不会创建请求或重启。`--restart` 通过 Windows Task Scheduler COM 提交一次正式控制器请求。入口本身不启动 PowerShell、不修改组策略或用户级执行策略、不修改平台检查设置。

入口先验证控制器已安装、启用及其工作目录一致；控制器忙时拒绝重复提交。写入请求采用临时文件、刷新到磁盘和原子替换。启动失败时仅清除自身尚未被领取的请求；请求已领取但结果不明时明确报告未知，不自动再发。实际重启仍由独立控制器管理。

回执 `accepted=true` 仅表示提交，不等于完成。必须核对 `state/core-controller-report.json` 中同一个 `request_id` 的结果、退出码和实际服务验证。在生产维护前核对活动任务，避免影响其他工作。

旧 `.ps1` 文件保留为兼容入口；直接执行旧脚本仍受系统脚本策略约束。不要把新维护入口误称为关闭全系统安全检查。

## HTTP 观测

HTTP 入口新增只记录元数据的事件：

| 事件 | 含义 |
| --- | --- |
| `http_received` | 请求已到达本机 `/mcp` HTTP 包装层 |
| `http_response_started` | 开始生成响应，保留 HTTP 状态及本机入口拒绝状态 |
| `http_tool_receipt` | 某个工具操作编号对应的 HTTP 请求编号 |
| `http_dispatch_exception` | 本机 HTTP 派发或交付异常，只记录异常类型 |
| `http_finished` | HTTP 处理结束，以及完整响应是否已交付给服务器发送接口 |

HTTP 响应头 `X-CCM-Request-ID` 和工具回执 `http_request_id` 由服务器生成，不采用客户端提供的同名值。工具原有 `operation_id` 保持不变。HTTP 200 仅代表该 HTTP 响应状态，不代表工具或命令成功，仍须检查 `ok`、退出码及业务验收。

`gate_status` 有值表示本机 OwnerHTTP 入口明确生成了拒绝响应；为空则不能据状态码认定是该入口拒绝。只有 HTTP 接收记录而无工具处理器记录时，应继续检查协议、SDK 与传输；连 HTTP 接收记录都没有时，先核对日志覆盖及入口可用性，不能从缺失记录猜测上游内部算法。

观测器不记录 HTTP 头、查询参数、请求正文、响应正文、环境值或文件内容，不增加自动重试，不更改鉴权、速率限制、工具注解、官方运行模式或审批结果。

## 本次回归约定

集成测试中主动终止进程后的续读，不再要求 `ok=true`。非零退出必须对应 `command_failed` 和命令进程来源；原会话退出状态及禁止控制非本桥会话的断言保留。浏览器验收更新陈旧的工具总数（41 → 48）和默认端口（8767 → 8774），动作链与旧快照拒绝测试不放宽。

原平台拦截的内部判定原因不在本机接口的可观察范围内。新增观测能力不能被描述为已经解除平台拦截。生产日志与原始证据保留在被 Git 忽略的 `evidence` 目录，不上传支付配置、凭据或本机完整日志。
